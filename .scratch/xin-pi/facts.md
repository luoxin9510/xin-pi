## 1. Repo conventions

- Root `AGENTS.md` (read it before any code): no `any` unless needed (biome has `noExplicitAny` off, but the rule stands), no runtime checks of typed values, no inline imports, erasable TS only (strip-types: no enums, parameter properties, namespaces), never `git add -A`, commit message `{feat,fix,docs}[(scope)]: msg`, "Never run `npm test` unless requested", never run the full vitest suite directly. After code changes: `npm run check` (full output). Packages other than `chord` may ignore the Chord v2 style section.
- `CONTRIBUTING.md` is the upstream contribution gate (approval by maintainers, `lgtm`). It does not apply to our own fork's PRs, but "core stays minimal, features are extensions" is the upstream taste: our core diffs should be small to keep merges cheap.
- Biome (`biome.json`): tabs, indentWidth 3, lineWidth 120, `recommended` rules. Covers `packages/*/src/**/*.ts` and `packages/*/test/**/*.ts`. pi-pipipi is written with 2-space indent and no build: `npm run check` (runs `scripts/biome-check.mjs --write`) will reformat it all (expect a large whitespace diff in the move commit; do the move in its own commit).
- Root `tsconfig.json`: `noEmit`, `paths` map every workspace package name to its `src/index.ts` (so type checking never needs a build). `include` has `packages/*/src/**/*` and `packages/*/test/**/*`. A new package needs a `paths` entry for `@xin-pi/pipipi`.
- Root `npm run check` = biome write + `check:pinned-deps` (workspace deps pinned to exact versions) + `check:runtime-deps` (every runtime import of a public package must be declared in its package.json; `private: true` packages are skipped, see `scripts/release-packages.mjs`) + `check:ts-imports` (relative imports need `.ts`) + `check:entry-graphs` + `check:install-lock:coding-agent` + `tsc --noEmit` + examples tsc + browser smoke.
- Root `npm run build` is a hard-coded chain: telemetry, schema, chord, tui, codemode, mcp, ai, durable, env, agent, coding-agent. A new package that coding-agent needs at build time must be inserted there (before coding-agent). Each package builds with `tsc -p tsconfig.build.json`, coding-agent additionally runs `scripts/build-coding-agent-bundle.mjs` (esbuild, bundles `dist/cli.js`, `index.js`, `rpc-entry.js` into `dist/bundle/`; `cli.js` there is a 3-line launcher requiring `cli-runtime.js`).
- Root `workspaces` is `packages/*`, so `packages/pipipi` is a workspace automatically. `npm test` at the root = `test:scripts` + `npm run test --workspace packages --if-present`, i.e. it runs the `test` script of EVERY package. `./test.sh` runs that under `env -i` (no API keys, no auth). Consequence: a `test` script in packages/pipipi that needs haiku, git identity, a pty or `~/.pi/agent/auth.json` would fail in `./test.sh` and in root `npm test`. See open question 2.
- Tests: coding-agent, codemode, mcp use vitest (`vitest --run`; `vitest.config.ts` sets `PI_OFFLINE=1`). Run one file from the package root: `node "$(git rev-parse --show-toplevel)/node_modules/vitest/dist/cli.js" --run test/x.test.ts`. `packages/tui` uses `node:test`. coding-agent integration tests use `test/suite/harness.ts` + the faux provider (no real keys). pi-pipipi uses `node --test --experimental-strip-types` (Node >=22.18; root engines should be checked; strip-types is the default on 24).

No build needed. Note the `--import` flag lives in `process.execArgv`, which matters for child processes (section 5).
- codemode split: `packages/codemode` is the generic sandbox (QuickJS wasm worker, `CodemodeSandbox`, declarations; no pi knowledge). `packages/coding-agent/src/extensions/codemode/` is the pi integration: `index.ts` (`createCodemodeExtension(options)`: registers the tool with `defaultActive: false`), `tool.ts` (tool definition, description, nested-call types, `CodemodeToolOptions`), `execute.ts` (`executeCodemode`, loaded lazily via `execute.lazy.ts`), `renderer.ts`, `worker.ts`.

All are still exported from `packages/coding-agent/src/index.ts`. If coding-agent's `extensions/index.ts` imports `@xin-pi/pipipi` and pipipi imports `@earendil-works/pi-coding-agent`, that is a package cycle (tsc build order, `rootDir: ./src` in `tsconfig.build.json`, the esbuild bundle starts from `dist/`). See open question 1.
- CLI bin: `packages/coding-agent/package.json` has `"bin": { "pi": "dist/bundle/cli.js" }`, `"piConfig": { "configDir": ".pi" }`, name `@earendil-works/pi-coding-agent`, plus a `./rpc-entry` export (`dist/bundle/rpc-entry.js`: forces `--mode rpc`, sets `process.title`).
- Naming derives from `package.json` `piConfig` of the package found from the entrypoint (`config.ts` `getPackageJsonPath`/`getPackageDir`, ~L578-611): `APP_NAME = piConfig.name || "pi"`, `CONFIG_DIR_NAME = piConfig.configDir || ".pi"`, `ENV_AGENT_DIR = <APP_NAME upper>_CODING_AGENT_DIR`, `ENV_SESSION_DIR = <APP_NAME upper>_CODING_AGENT_SESSION_DIR`, `getAgentDir()` = env dir or `~/<configDir>/agent`, debug log `<APP_NAME>-debug.log`, process title and help text use APP_NAME. So adding `"piConfig": { "name": "xpi", "configDir": ".pi" }` gives: command/help/title `xpi`, config dir still `~/.pi/agent` (shared), but the override env vars become `XPI_CODING_AGENT_DIR` / `XPI_CODING_AGENT_SESSION_DIR` (a `PI_CODING_AGENT_DIR` exported in the shell would be ignored by xpi). Other env names are literal `PI_*` (`PI_OFFLINE`, `PI_SKIP_VERSION_CHECK`, `PI_CODING_AGENT=true`, ...) and do not change.
- What adding `xpi` takes: (a) rename the bin key in `packages/coding-agent/package.json` to `xpi` (keep `dist/bundle/cli.js`) and set `piConfig.name`; or (b) a new `packages/xpi` launcher package. Do not keep both `pi` and `xpi` bins in a package that is `npm link`ed or globally installed: it would overwrite the global `pi`. Two things to neutralise for xpi: `utils/version-check.ts` (`https://pi.dev/api/latest-version`, would announce upstream pi releases) and self-update / installer paths (`PACKAGE_NAME`, `package-manager-cli.ts` `DEFAULT_INSTALLER_API_BASE`); `PI_SKIP_VERSION_CHECK=1` skips the check.

## 3. Where "move to background" fits in the codemode built-in

How a script runs today (`extensions/codemode/tool.ts` L439 -> `execute.ts` `executeCodemode(toolCallId, params, signal, onUpdate, ctx, options)`):
- `execute` builds `sandboxTools` for `ctx.tools`; each nested call goes through `ctx.executeTool(name, args, { signal: callSignal })` (ExtensionToolContext, `types.ts` L397-415). `ctx.executeTool` is bound to the calling tool call id by `agent-session.ts` L3622 -> `_executeNestedToolCall(parentToolCallId, ...)` -> `NestedToolCallRunner.execute(callerId, ...)` (`core/nested-tool-calls.ts`).
- The script runs in `CodemodeSandbox.execute(code, { signal, store })` (a worker, wasm, deadline from `timeoutMs`). `signal` is main's tool signal (Esc aborts it). The function resolves with a single `AgentToolResult` when the script ends; there is no way to return early.
- Nested ids: `scope.nextId++` in `NestedToolCallRunner.execute` gives `<callerId>/<n>`. `takeRecord(toolCallId)` (called from `agent-session.ts` L1168-1173 on the `toolResult` `message_start`) DELETES the scope of the caller and snapshots its recorder into `message.nestedCalls`; `clear()` runs at `agent_end`. So after the codemode tool returns early:
  - a later nested call from the still-running script creates a NEW scope for the same caller id with `nextId = 1`: ids `<callerId>/1`, `/2` repeat the ones used before the early return (duplicate ids in `tool_execution_*` events; pipipi's prefix matching still works but ids are no longer unique);
  - the new recorder is never taken (usage/cost of nested calls after the move is not recorded anywhere);
  - `agent_end` `clear()` drops scopes, again resetting ids.
  I inferred this from reading, not from a run; ticket 2 must prove it with a test and fix it in `NestedToolCallRunner` (a `detach(callerId)` that keeps the scope and counter alive until the script really ends, and a `release(callerId)` at the end).
- `NestedToolCallRunner` serialises "exclusive" nested calls on one queue when `agent.toolExecution === "sequential"` or the tool has `executionMode: "sequential"`; a background script's calls would then queue behind main's. Agent is parallel by default; note it, test it.
- `_findLastAssistantMessage()` is used for hook context of every nested call; after the move the "last assistant message" may be a later turn's: harmless but worth knowing.
- `appendEntry` (store writes) happens at script end, after the early return: it appends a session entry while main may be mid-run; already true in v3a (verified there).

Proposed API shapes (recommend A):

A. Typed controller, exported from coding-agent (`extensions/codemode/scripts.ts`, re-exported from `src/index.ts` next to `createCodemodeExtension`):
```ts
export interface CodemodeScriptInfo { id: string; toolCallId: string; sessionId: string; startedAt: number; state: "foreground" | "background" | "ended" }
export interface CodemodeScripts {
  owner(nestedToolCallId: string): CodemodeScriptInfo | undefined;   // by "<codemode call id>/<n>" prefix
  background(scriptId: string, result?: string): boolean;            // codemode call returns early with `result` (default text), script keeps running detached from main's signal
  backgroundAll(sessionId: string): boolean;                         // ctrl+b
  stop(scriptId: string): Promise<boolean>;                          // abort the detached script's own controller
  subscribe(l: { onStart?(s): void; onEnd?(s, outcome: { result?: AgentToolResult; error?: Error; stopped: boolean }): void }): () => void;
}
export const codemodeScripts: CodemodeScripts;
```
`executeCodemode` registers every script (foreground), creates its own `AbortController` linked to main's signal only while foreground (exactly what `src/background.ts` does today), races the sandbox against the "moved" promise, on move returns `{ content: [text], details: { ...snapshot, background: true, scriptId } }`, and on real end calls `onEnd`. pipipi keeps all policy (when to move, the end message, the registry rows, delivery with `sendMessage`); codemode keeps only the mechanism. The singleton is safe because builtins and pipipi share one module instance in the bundle; for the dev/jiti path, the same applies to builtins (they are imported, not jiti-loaded).

B. Event bus only (no new export): `pi.events` (`core/event-bus.ts`, `emit/on` of string channels, sync, handler errors only logged). pipipi emits `codemode:background` `{ toolCallId }` (the owner is resolved by codemode from the prefix), codemode emits `codemode:script-started`/`codemode:script-ended` `{ scriptId, toolCallId, ok, content, details }` and listens to `codemode:stop` `{ scriptId }`. Pro: no export surface, survives module duplication. Con: untyped, no return value (move result arrives by another event), no `list()` for the panel; this is why it is the fallback.

Settings: a foreground script keeps today's behaviour with no extension loaded (nothing calls `background`). The ctx-without-UI rule from v3a (print mode exits at turn end, so do not move) stays in pipipi.

Port that function into packages/pipipi (add `process.execArgv` before `argv[1]`), use it when `pipipi.piCommand` is unset, keep `piCommand` and `PIPIPI_TEST_PI` as explicit overrides. The `-e` path for the codemode-only child: in xin-pi it can be `-e builtin:codemode`-style via a new tiny builtin or keep `child-codemode.ts` (file path resolved from the package, as `getPackageDir` helpers do); decide in ticket 3 (`--no-extensions -e builtin:codemode` reproduces the parent test seam of v3a, but the child needs mode "only").
- Children inherit `XPI_CODING_AGENT_DIR` through `process.env` automatically, so a test sandbox dir applies to children too.
- `PIPIPI_DEPTH=1` nesting guard stays.
