xpi-graph

给 xpi 加一种用图来控制流程的方式。流程里的硬规则写成图上的边，模型只能沿着边走，在每个节点内部照常自由工作。

状态 拷问两轮已完成（20 条已定），还没开始实现 日期 2026-11-17 下一步 你批准 spec 后按里程碑实现

要解决的问题

xpi 现在的流程规则写在提示词和记忆里，靠模型每次都读到、理解对、并且照做。规则大多是出过事之后补上的：CI 失败时 PR 被合并了，之后才有“合并前先看 CI”；spec 没经过拷问就被动手实现了，之后才有“spec 要先拷问”。

提醒只能降低出错的概率。图把规则变成结构：两个节点之间没有边，模型就没有办法走过去。

目标，和第一版不做的事

目标
  • 硬规则由结构保证，不靠提醒。
  • 每个节点可以用不同的模型，把 relay 的省钱方式用到任意流程上。
  • 随时看得到流程走到哪一步，退出重开后接着走。
  • 不用图的时候，xpi 的行为和花费完全不变。
第一版不做
  • 让模型自己画图。
  • 并行节点、子 agent 节点。
  • 把 relay、workflow、/review 迁到图上。
  • 搬上游的 durable 和 chord。只借思路。

核心概念

图由节点和边组成。节点是同一个会话里的一段工作，它只是换了一套设定：角色提示、模型、限制（禁止的命令、不许写的路径）。边说明从一个节点可以去哪个节点，以及怎样才算可以走。

一条原则贯穿全部设计：边是硬的，节点内部是自由的。在节点里模型想怎么做都行，xpi-graph 不管；离开节点只能走声明过的边。

出口谁决定例子
模型选模型调 next，从这个节点允许的边里挑一条，并交一份报告实现完成，交去审核
命令判跑一条命令，按退出码走测试通过才往下，失败就回去改
人批准停下来等你拷问的结论等你点头

回头的边（比如“审核不过，回去改”）带一个最多几轮的上限，到了上限就停下来找你。加载时会找出所有构成环的边，没写上限的默认 3 轮。

一个例子：开发流程

你现在的开发流程本身就是一张图，三种出口都用得上。

图是一个 JS 文件，默认导出一个对象。项目里的放 .pi/graphs/（只在受信任的项目里读），个人的放 ~/.pi/agent/graphs/，项目的优先。这和保存的 workflow 是同一套规矩。

// .pi/graphs/dev.js
export default {
  name: "dev",
  start: "grill",
  nodes: {
    grill:  { model: "opus",   prompt: "拷问需求，列出要定的事", readOnly: ["**"] },
    spec:   { model: "opus",   prompt: "把结论写成 spec" },
    build:  { model: "haiku",  prompt: "按 spec 实现，只改 spec 提到的文件",
              deny: ["gh pr merge", "git push origin main"] },
    ci:     { run: "gh pr checks --watch", timeout: "30m" },
    review: { model: "opus",   prompt: "派一个新上下文的 Opus 子 agent 审核改动，汇总它的结论" },
    merge:  { run: "gh pr merge --squash" },   // 引擎执行，不交给模型
  },
  edges: [
    { from: "grill",  to: "spec",   exit: "approve" },
    { from: "spec",   to: "build",  exit: "approve" },
    { from: "build",  to: "ci",     exit: "model" },
    { from: "ci",     to: "review", exit: "pass" },
    { from: "ci",     to: "build",  exit: "fail", max: 3 },
    { from: "review", to: "merge",  exit: "model", label: "通过" },
    { from: "review", to: "build",  exit: "model", label: "有问题", max: 3 },
  ],
  // 加载时检查：到 merge 的每条路径上，最后一次进入 build 之后必须再有一次 ci 通过
  requires: [{ before: "merge", passed: "ci", notAfter: ["build"] }],
};

它怎么运行

整张图跑在一个会话里。前提是 xpi 只用 codemode。

  • 换节点：模型在 codemode 里调转移工具 next({ to: "ci", report: "…" })。to 是目标节点名，report 必填。目标不在当前节点的出边里就报错，并列出可选的节点。调用成功后，下一次请求换成新节点的模型和角色提示。这和 relay 换 lead、worker 的机制相同。
  • 进入节点：引擎发一条消息，写明现在在哪个节点、角色提示、可以去哪几个节点以及各自的含义。
  • 人批准：模型请求走一条要批准的边时，弹出一个三选一：批准、退回、停止图。选退回后，你的下一条消息就是意见，模型留在当前节点继续。没有界面时算退回并停下。
  • 命令节点：引擎跑一条固定的命令，按退出码选边。默认超时 10 分钟，节点可以用 timeout 改，超时算失败。输出的最后 200 行写进会话，下个节点看得到。第一版没有图变量。
  • 模型没选边就结束回合：节点的出口里有“人批准”的，这是正常的，它在等你说话。其他节点提醒一次，再不选就停下来找你。
  • 一个会话一张图：图运行期间模型由节点决定，relay 不参与；节点没写模型就用启动图时的模型。走到终点或执行 /graph stop 后，恢复启动前的模型和工具。
  • 记录：每次进入节点，往会话里写一个节点条目。它就是这一步的存档点。
  • 状态：不另外存。沿当前分支把节点条目读一遍，就知道现在在哪个节点、回头改了几轮。
  • 图的锁定：图必须是纯数据，不能有函数。/graph start 时把整张图写进会话的启动条目，之后运行、恢复、分叉都读这一份，不再读文件。运行中改文件只影响下一次启动。
  • 接着走：退出重开后，最后一个节点条目就是当前位置。
  • 重跑：会话本来就是一棵树。你想重做某一步，就从那个节点条目分叉，旧的尝试留在旁边的分支上。

强控制怎么保证

图只管“走哪条边”是不够的。“实现”节点有 bash，模型可以不走边，直接运行 gh pr merge。所以控制分三层，每层能保证的程度不同。

层保证程度靠什么
走哪条边强转移工具只列出当前节点允许的边，由代码执行。直接调别的转移会被钩子拦下。
闸门的结果强命令由引擎跑、引擎读退出码，模型不能谎报通过。人批准走界面对话框，模型不能替你点。
节点里的动作防跳步，不防蓄意绕过敏感动作由引擎执行；模型节点另配一份禁止命令的清单作兜底。

第一版做的三样

  1. 敏感动作做成命令节点。比如“合并”由引擎在边走通之后执行。模型节点可以配两种限制作为兜底：deny 是禁止的命令文本，readOnly 是这个节点不许写的路径。
  2. 加载时证明规则成立。在图上声明“到达合并之前必须经过 CI 通过，而且最后一次进入实现之后必须再过一次”，加载时检查每一条通往合并的路径。图画错了当场报错。
  3. 出问题一律停下。没有界面时，人批准算不通过；状态读不出来就停下来找你，不猜着继续；子 agent 继承当前节点的限制。

另外两处也要堵上：图在启动时整张写进会话并锁定，运行中改文件不生效；图运行期间引擎自动把图文件目录和会话文件设成只读。检查命令用到的配置（比如 package.json、CI 配置）实现节点可能有正当理由改，所以不自动保护，由图的作者在节点上用 readOnly 写。

要说清楚的边界：这三样保证的是流程不被跳过，防的是模型忘记规则或图省事。模型在节点里有 bash，蓄意绕过禁止命令清单总是可能的（比如把命令写进脚本再执行）；它也可以把测试改成能过，这只能靠独立审核发现。真正的硬隔离要靠凭据隔离或沙箱，第一版不做。

结构

做法和 relay 一样分两半：一个不依赖 coding agent 的纯逻辑包，加上 coding agent 里的一层接线。纯逻辑包叫 xpi-graph，接线层是内置扩展 builtin:graph。relay 里的转移表引擎是它的内部文件，形状是“状态加事件”的表，和“节点加边”对不上，所以 xpi-graph 自己写一个小的解释器，relay 一行不动。

第一版的范围

原则是简单有效，先让一张手写的图能可靠地跑完，别的以后再加。

里程碑

四个，每个一个 PR。每个 PR 等 CI 通过，再由新上下文的 Opus 审核，过了才合并。真模型测试只用 Haiku。

  1. 纯逻辑包 xpi-graph：图的校验、“必须先通过”检查、从条目算状态。只有离线单元测试。
  2. builtin:graph 最小可跑：/graph start、/graph、/graph stop，会话内节点换模型和角色提示，next 工具，节点条目，状态行，退出重开接着走。做完后用 Haiku 实测缓存花费。
  3. 强控制：命令节点、人批准、deny 和 readOnly、环的上限、提醒一次再停、/graph goto、子 agent 继承限制。
  4. 两张图和文档：开发流程图、发版流程图、真 Haiku 全流程检查、文档。
以后再做为什么先不做
节点的工具白名单xpi 只用 codemode，按工具限制要改 codemode 内部。第一版用 deny 和 readOnly 代替。
边上压缩上下文比如审核者只看改动，不看实现过程。有用，但要先看节点切换对缓存和花费的实际影响。
每个节点的花费统计用量条目已经有了，按节点分段汇总即可。等节点条目稳定后加。
模型选用或临时画图模型自己画的图要先经你批准才能变硬，需要多一套交互。
并行节点、子 agent 节点第一版只做会话内节点。需要新上下文时（比如独立审核），节点里的模型用现有的 Agent 工具派子 agent。
等很久的事交给后台比如等远程 CI。以后接到 roost 上，第一版的命令只在本地跑。
TUI 图面板、Herdr 显示状态行先够用。
凭据隔离、沙箱防模型蓄意绕过需要它们，比如合并用的 token 只在“合并”节点里存在。工作量是另一个量级。

和现有功能的关系

功能它是什么和 xpi-graph 的关系
relay一个会话里两个模型交接，形状固定第一版不动，图运行期间 relay 不参与。以后变成 xpi-graph 上的一张内置图。
workflowcodemode 脚本，编排多个子 agent并存。workflow 管多个 agent，xpi-graph 管一个会话里的流程。
agent teams多个 agent 组队无关，不受影响。
roost后台会话和定时任务第一版无关。以后用它来等待和唤醒。

xpi 已经有四套编排机制。xpi-graph 值得做的前提是它最终能收编其中一部分，至少是 relay 和 /review 这类固定流程。

怎么算成功

  • 用开发流程这张图跑三个真实任务，没有一次能在 CI 失败的情况下走到合并。
  • 在“实现”节点里让模型直接合并，会被拦下，并留下一条记录。
  • 把图里的 CI 节点删掉再加载，当场报错，不能开始。
  • 中途退出再打开，回到同一个节点、同一轮。
  • 写一张新图不超过 30 行，不用读 xpi-graph 的代码。
  • 除开发流程外再写一张发版流程的图并跑通，引擎不用为它改代码。
  • 不启动图时，xpi 的请求和花费与现在没有差别。
  • relay 的测试原样通过，说明没有碰到它。

风险，和还没定的事

  • 换节点会打断提示词缓存。换模型一定会断，同一个模型换系统提示词也会断。节点不能切得太碎；所以定一条规则：相邻节点模型相同时，角色提示作为消息发出，不改系统提示词。花费在第一个里程碑做完后用 Haiku 实测，结果不好再调整。
  • 禁止命令清单拦不住蓄意绕过。它只匹配命令文本，xpi 现有的路径保护也不解析 bash。第一版接受这一点，文档里要写明。
  • 反复用的流程可能没几条。接受这个风险先做。开发流程的图不随 xpi 内置，放在本仓库的 .pi/graphs/dev.js，兼作例子和测试用图；再用发版流程检验引擎是不是真的通用。

已经定下的事

  • 节点是会话内节点。
  • xpi 只用 codemode，换节点的工具只在 codemode 里。
  • 边是硬的，节点内部自由。
  • 借 LangGraph、durable、chord 的思路，不搬代码，不引入 chord。
  • 第一版要简单有效，功能以后再加。
  • 强控制第一版做三样：敏感动作做成命令节点、加载时检查规则、出问题就停。目标是防跳步，不防蓄意绕过。
